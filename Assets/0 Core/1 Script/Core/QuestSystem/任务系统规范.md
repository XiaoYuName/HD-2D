# 任务系统规范（程序侧）

策划原文见 `任务系统相关策划内容.txt`。本文是把它翻译成可配置、可实现的规范。

## 0. 四张表

配置拆成三张互相引用的表（外加一张纯展示表），**三层都能配奖励**：

| 表 | 一行是什么 | 关键列 |
| --- | --- | --- |
| `QuestCategoryData.xlsx` | 一个任务类别（章节），面板左侧一个页签 | `QuestId`（`+` 分隔的任务ID列表）、`Reward` |
| `QuestDataConfig.xlsx` | 一个任务 | `QuestTrigger`、`AcceptCond`、`NameKey`/`DescKey`/`IconKey`、`QuestObjData`（`+` 分隔的目标ID列表）、`ObjInOrder`、`Reward` |
| `QuestObjConfig.xlsx` | 一条任务目标（可被多个任务共用） | `QuestObjData`（一条目标写法）、`DescKey`（描述文案）、`Reward`、`ExtraCompleteCond`、`ExtraDescKey`、`ExtraReward` |
| `QuestRewardData.xlsx` | 奖励类型的图标与名称，纯展示 | `Id`（= `QuestRewardType` 名）、`NameKey`、`IconKey` |

对应的运行时类：`QuestCategory` / `QuestData` / `QuestObjConfigData`（Luban 生成类是 `QuestCategoryData` / `QuestDataConfig` / `QuestObjConfig`，别混）。

## 0.1 三个概念

| 概念 | 说明 | 配在哪 |
| --- | --- | --- |
| **领取触发**（Trigger） | 一个**瞬间事件**，发生时才去检查这个任务能不能领 | `QuestDataConfig.QuestTrigger` |
| **领取条件**（Cond） | 一个**持续状态**，触发发生时用它做门槛判断 | `QuestDataConfig.AcceptCond` → `QuestStoryCondData` |
| **任务目标**（Objective） | 领取后要达成的事，可累计进度 | `QuestObjConfig.QuestObjData` / `ExtraCompleteCond` |

策划原文的「领取方式」混了这三类。拆开的理由：

- 「进入区域触发」是事件，只能靠事件驱动；「NPC 数值达标」是状态，事件驱动会漏（数值可能在任何时刻变）。
- 状态判断（道具、好感、天数、前置任务）在剧情系统里也要用，所以独立成 `QuestStoryCondData`，两边共用。

一个任务可以只配触发（不配 `AcceptCond` = 无门槛）、只配条件（不配 `QuestTrigger` = 等同 `Auto`）、或两者都配。

## 1. 配置写法：位置参数

`QuestTrigger` / `QuestObjData` / `ExtraCompleteCond` / 各处 `Reward` 列用同一套写法：

```
一条 = 类型:参数1:参数2，多条用 / 分隔
例：DayPassed:2/CompleteGame:1001:2:1
```

- 类型名不区分大小写，各段两边的空白会被裁掉。
- **可选参数一律排在末尾**，不需要就整段省略；要跳过中间的可选参数就填 `0`（表示「不限」）。
- 加新目标类型不用改表结构，只加枚举 + 一个子类。

位置参数没有 key 可对照，所以每种类型在启动读表时报一次自己的写法，
段数不够或某段不是数字会在 Console 直接打出是哪一行、正确写法是什么：

```
[Quest] 目标 10005 的 "BuyItem" 参数不足（需要 1 个，实际 0 个），正确写法: BuyItem:道具ID[:件数]
[Quest] 目标 10005 的 "CompleteGame:1001:两次" 第 2 个参数 "两次" 不是整数
```

### 1.1 领取触发 `QuestTrigger`

多条之间是 **OR**：任意一个事件发生就尝试领取。

| 写法 | 状态 |
| --- | --- |
| `Auto` | ✅ 读档/任意事件后重扫（不配 `AcceptTrigger` 等同于此） |
| `EnterZone:场景ID` | ✅ 自动接管 |
| `ExitZone:场景ID` | ✅ 自动接管 |
| `EnterZoneStay:场景ID:停留秒数` | ✅ 自动接管 |
| `ClickNpc:NPC ID` | ✅ 需业务层上报 |
| `DialogNpc:NPC ID` | ✅ 需业务层上报 |
| `MiniGameEnd:小游戏ID` | ✅ 需业务层上报 |
| `MiniGameResult:小游戏ID:结果`（1 胜 / 2 负） | ✅ 需业务层上报 |
| `RandomChance:千分比` | ✅ 重扫时掷点 |
| `PlotEnd:剧情ID` | ⏳ 剧情完成记录未实现，永不触发 |

「NPC 数值达标」「游戏时间达到」「任务完成」不做成触发 —— 它们是状态，写进 `AcceptCond` 的
`NpcProp` / `Day` / `TimeSlot` / `QuestPre`。

### 1.2 任务目标 `QuestObjConfig`

一行一条目标，**一行只写一条**（多条要拆多行，任务用 `+` 把它们串起来）。
同一条目标可以被多个任务引用，配置只有一份。

任务下的多条目标之间是 **AND**：全部达成任务才完成。

| 写法（`[]` 内可省略） | 进度来源 |
| --- | --- |
| `DayPassed:天数` | 状态：`PlayerData.Day` 达到 |
| `Dialog:对话ID` | 状态：`DramaManager.HasDialogue` |
| `CompleteQuest:任务ID` | 状态 |
| `HoldItem:道具ID[:数量]` | 状态：`InventoryManager.GetItemCount` |
| `CharacterProp:NPC ID:数值[:属性类型]` | 状态，属性类型默认 Goodwill |
| `CompleteGame:小游戏ID:局数[:结果]` | 事件累计，结果 0 不限 / 1 胜 / 2 负 |
| `DialogNpc:NPC ID[:次数]` | 事件累计 |
| `DialogNpcWithItem:NPC ID:道具ID[:次数]` | 事件累计，每次消耗 1 个道具 |
| `GiveGift:NPC ID:礼物ID[:次数]` | 事件累计，礼物ID 填 0 = 任意礼物 |
| `BuyItem:道具ID[:件数]` | 事件累计，道具ID 填 0 = 任意道具 |

策划原文「与指定 1 个或多个 NPC 对话」——**不做「多个 NPC」的复合目标**，写成多条 `DialogNpc` 即可，
天然就是 AND；要 OR 的场景目前没有，真需要时再加，不提前设计。

同理，「1 条鱼 + 2 颗糖」写成两行 `HoldItem`，UI 一条一行各自一个进度。
真要合并成一条显示，就自己继承 `CountObjData`，在它的 `Info` 里开两个计数字段 —— 见 1.3。

### 1.3 静态数据与动态进度分开

一条目标拆成两个对象，**静态只有一份，动态一次领取一份**：

| | 类 | 存什么 | 生命周期 |
| --- | --- | --- | --- |
| 静态 | `QuestObjData` | 解析好的参数（道具ID、NPC ID…）、文案模板、校验规则 | 读表时造一份，整局共用 |
| 动态 | `QuestObjInfoBase` | 进度（`CountObjInfo.count`）＋ 事件订阅 | 每次领取一份，进存档 |

外面还有一层 `QuestObjConfigData` —— 目标表的**一行**：主目标 ＋ 可选超额 ＋ 各自的奖励，
即一行 = 两个 `QuestObjData` ＋ 两组奖励。

动态侧的 `Data`（静态引用）**不进存档，也不靠 id 反查**：一个 Info 是主目标还是超额，
看它挂在 `QuestObjStateInfo.target` 还是 `.extra` 上就知道了，由 `QuestObjStateInfo.Set` 直接注入
（新建和读档都会走到）。所以 Info 里连 `id` / `isExtra` 都不需要。

**没有 Refresh，也没有任何轮询** —— 每个目标订自己那一种事件，订阅时先按当前状态算一次。

订阅在**动态侧**（`QuestObjInfoBase.SubsEvents` / `UnsubsEvents`，由 `QuestObjStateInfo.Activate` / `Deactivate` 成对驱动）：
回调要作用于「我这一份进度」，本来就是每个实例一份。静态侧整局共用，存不了这种东西。

每种目标把自己的实例写成**嵌套类 `Info`**：

```csharp
public class DialogNpcObjData : CountObjData
{
    long npcId;                                      // 私有，不为了给 Info 看而放大
    public override QuestObjInfoBase CreateInfo() => new Info();

    public class Info : CountObjInfo
    {
        DialogNpcObjData ObjData => (DialogNpcObjData)Data;
        public override void SubsEvents() => QuestEventBus.NpcTalked += OnNpcTalked;
        public override void UnsubsEvents() => QuestEventBus.NpcTalked -= OnNpcTalked;
        void OnNpcTalked(long talkedNpcId) { if (talkedNpcId == ObjData.npcId) Advance(1); }
    }
}
```

嵌套是为了让 Info 直接读到外层的私有参数，于是回调是**普通命名方法**而不是闭包，
`+=` / `-=` 用方法组即可（那几个字典型注册接口内部是 `Action -= callback`，按委托相等性摘，方法组没问题）。

#### 三个族：不让一个 int 兼职布尔

达成条件长什么样，签名就长什么样。没有「返回 0/1 当 bool 用」这种事，也不给布尔型硬凑一个 `Need => 1`：

| 静态基类 | 判定 | 子类要实现 | 嵌套 Info 继承 |
| --- | --- | --- | --- |
| `FlagObjData` | 成没成（到第几天、做过某段对话、某任务完成了） | `IsMet()` 返回 bool + `CreateInfo()` | `FlagObjInfo`：**零字段**，订变化事件，回调里 `NotifyChanged()` |
| `AmountObjData` | 现在有多少（持有数、好感度） | `Need` + `GetAmount()` 返回当前量 + `CreateInfo()` | `AmountObjInfo`：**零字段**，现算现比 |
| `CountObjData` | 累计几次（打几局、送几次礼） | `Need` + `CreateInfo()` | `CountObjInfo`：`count` 进存档，回调里 `Advance()` |

前两族**不存状态**，每次现问世界，两个后果都是要的：

- 卖掉道具、好感掉了，`AmountObjData` 的进度跟着回退；
- 领任务**之前**就已经聊过那段对话、前置任务早就做完了，订阅后那一次判定照样能捞到达成。

> 所以这两族不能改成「在 Info 里存个 `bool isArrived`，靠事件写」——事件早就发过了，那条目标会永远做不完。
> 真出现世界状态查不到的一次性 flag（比如没有「当前区域」可查的到达判定），那才是第四族：
> 照 `CountObjInfo` 的样子在它自己的 `Info` 里开 `public bool met;` 存进存档。现在没有这种目标，不提前建类。

`ProgressText`（"1/2"）在 Info 上——只有动态侧算得出来；文案模板在静态侧。
两边由 `QuestObjData.GetDesc(progressText)` 合成完整描述，UI 只用 `QuestObjStateInfo.Desc` 这一个出口。
`{Value}`（要多少）由 `AmountObjData` / `CountObjData` 这两个族基类填，`FlagObjData` 没有这个概念也就不填；
叶子类只重写 `SetDescVars` 补自己的 `{ItemName}` / `{CharacterName}` 之类。

#### 描述文案：全部来自配表

代码里**没有**类型自带的默认文案。主目标读目标表的 `DescKey` 列，超额条件读 `ExtraDescKey` 列，
`QuestObjConfigData` 读表时注入。配了超额却不填 `ExtraDescKey` 会在启动校验里 LogError（界面上本来会是一行空白）。

`QuestDataLoc.csv` 里 `QuestObj/*` 那批是**通用说法**（「持有 {ItemName} ×{Value}（{Progress}）」），
想用就把 Key 填进表里；想写剧情化的（「去铁匠铺问问张三炉子的事」）就自己加一条。
能用哪几个占位符由目标类型决定（见上面两段），填错了不报错，只是显示不出来。

`DescKeyOverride` 是代码侧的临时覆盖，只给测试用。

各目标订的事件：

| 目标 | 事件源 |
| --- | --- |
| `DayPassed` | `GameDataManager.RegisterPlayerDataDayChange` |
| `Dialog` | `QuestEventBus.DialogueFinished` |
| `CompleteQuest` | `QuestEventBus.QuestCompleted` |
| `HoldItem` | `InventoryManager.RegisterItemIDChangeCallBack`（按道具ID） |
| `CharacterProp` | `CharacterManager.RegisterCharacterBagChange`（按角色ID） |
| 累计型 5 种 | `QuestEventBus` 对应事件 |

**状态型**目标随事件重算，回退（比如道具被卖掉）也会跟着回退；**事件累计型**只增不减。

### 1.3.1 存档：直接存目标对象

存档存的就是 `QuestInfo`（含 `QuestObjStateInfo[]`，每个里面挂 `target` / `extra` 两个 `QuestObjInfoBase`），
序列化器开了 `TypeNameHandling.Auto`，子类类型写进 json 的 `$type`（嵌套类写成 `DialogNpcObjData+Info`），
所以**想存什么类型的进度就开什么字段**。

**配置数据根本不在存档对象上**（都在 `QuestObjData`），所以策划改了数量/条数读档立刻生效，
老存档不会把旧数值冻住。存档实例与当前静态类型对不上时按配置新建，不炸档。

### 1.2.2 有序目标 `ObjInOrder`

默认 `False`：任务下的目标乱序完成，全达成即可。填 `True` 则必须按 `QuestObjData` 里的**书写顺序**逐条完成。

实现上不是"判定时排个序"，而是**同时只让当前那一条监听事件**（`QuestInfo.Activate` → `ActivateCurrent`，
上一条完成后 `OnObjCompleted` 里再挂下一条）。必须这么做：要是把后面的目标也订上，
`HoldItem` 这类状态型目标会因为玩家身上早就有那个道具而立刻达成并发奖，顺序就白配了。

顺序状态不进存档 —— "第一条未完成的目标"（`QuestInfo.CurrentObj`）从各目标的 `completed` 标记就能推出来。
面板上还没轮到的目标行整行灰掉（`QuestObjRow` 根节点的 `CanvasGroup`）。

**什么时候别用它**：如果这几步之间还要插对话、分别发奖、或者玩家应该看到"这是一段任务链"，
那就拆成多个任务，用后一个任务的 `AcceptCond`（`QuestPre`）或 `CompleteQuest:任务ID` 目标串起来——
这也是魔兽的做法（WoW 单个任务里的目标一律并行，顺序全靠任务链）。
`ObjInOrder` 只解决"一个任务、一张卡、三步走"。

### 1.2.1 超额 `ExtraCompleteCond` / `ExtraReward`

超额挂在**目标**上，不在任务上。写法就是一条目标（复用同一套类型），判定窗口是
**主目标完成的那一刻**：那一刻超额条件也满足才发 `ExtraReward`，之后再满足不补发。

面板上超额**单独一块**（`ExtraRoot`：标题 ＋ 每条一行 `QuestObjExtraRow`），放在目标列表下面隔开一段，
不是挂在对应目标行的尾巴上 —— 一条目标一行，读起来才不串。行首的「目标N」指回它挂在第几条目标上。
主目标完成而超额没达成，整行灰掉（永远错过了）。

### 1.3.2 三层奖励的发放时机

全自动，玩家不用点任何领取按钮：

| 层 | 什么时候发 | 谁发 |
| --- | --- | --- |
| 目标奖励 `QuestObjConfig.Reward` | 该目标达成那一刻 | `QuestObjStateInfo.CheckComplete` |
| 超额奖励 `QuestObjConfig.ExtraReward` | 同上，且超额条件同时满足 | 同上 |
| 任务奖励 `QuestDataConfig.Reward` | 全部目标达成 → 自动交付 | `QuestManager.CompleteQuest` |
| 类别奖励 `QuestCategoryData.Reward` | 该类别下所有任务都完成，只发一次 | `QuestManager.TryRewardCategories` |

目标一旦达成就**定格**（`QuestObjStateInfo.completed`）并退订事件，持有类目标把道具卖了也不会把已发的奖励收回去。

### 1.4 奖励写法

和目标同一套写法。**一种 `QuestRewardType` 一个实现类**，类型名直接就是奖励的东西：

| 写法（`[]` 内可省略） | 实现类 |
| --- | --- |
| `Item:道具ID[:数量]` | `ItemQuestReward`，数量默认 1 |
| `Coin:数值` | `CoinQuestReward` |
| `GameCoin:数值` | `GameCoinQuestReward` |
| `Affection:NPC ID:数值` | `AffectionQuestReward` |

例：`Coin:100/Affection:10001:10`。

加一种奖励 = `__enums__.xlsx` 的 `QuestRewardType` 加一项 + 写个 `IQuestReward` 实现 + `QuestRewardFactory` 注册，
和加任务目标完全一样。玩家属性类的直接继承 `PlayerPropQuestReward`，只需给 `PropType` / `RewardType` / `DescKey` 三行。

UI 上的奖励图标走 `IQuestReward.GetView()` → `QuestRewardView`：道具类从道具表取 `IconName`，
其余类型按 `QuestRewardType` 名去 `QuestRewardData.xlsx` 查 `IconKey` / `NameKey`。

### 1.5 两层校验（触发 / 目标 / 奖励通用）

都在 `QuestManager.Start()` 读完三张表后跑完：

| 层 | 查什么 | 在哪 |
| --- | --- | --- |
| `Init` 里的 `Require` | 段数够不够、参数是不是数字 | 各实现，正确写法常量在 `QuestTriggerUsage` / `QuestObjUsage` / `QuestRewardUsage` |
| `Validate()` | 道具/角色/任务 ID 在表里存不存在、数值是不是正数 | `QuestConfigValidator`，报错用的字段名常量在 `QuestFieldName` |

因为启动就查过了，运行时**不做空判兜底** —— 查不到就是配置错了，该在 Console 里被看见。

`GetDesc()` 走多语言，Key 常量在 `QuestLocKey.Reward`（`QuestReward/Item` 这种斜杠分段，别写魔法字符串），
文案在 `Assets/0 Core/1 Script/Data/QuestSystem/QuestRewardDataLoc.csv`（表 `LocTableSet.QuestSystem`），
占位符 `{Value}` / `{ItemName}` / `{CharacterName}` 见 `QuestLocVar`（目标和奖励共用一套名字）。

任务奖励一般一次性、不复用，所以直接写在配置行里，不走 `RewardData` 索引表。
奖励在读表时就解析成对象并校验写法，发放时不再碰字符串。

## 2. 任务状态机

```
None ──触发+条件满足──> Available ──接受──> InProgress ──目标全达成──> ReadyToComplete ──自动──> Completed
```

- 交付是**自动**的：`QuestManager.OnQuestStateChanged` 一看到 `ReadyToComplete` 就立刻调 `CompleteQuest`。
  `ReadyToComplete` 这个状态和 `CompleteQuest` 这个公开方法都保留着 —— 以后要改回「点一下才交付」，
  把 `OnQuestStateChanged` 里那一行调用删掉、改由 UI 调 `CompleteQuest` 即可。
- 离开 `InProgress` 时目标自动退订事件（`QuestInfo.Deactivate`），已完成的任务不会再吃事件。

## 2.1 运行时对象层次

```
QuestInfo（存档单位，一个已领取任务）
└ QuestObjStateInfo[]（存档单位，一条目标的实例：completed / exceedAchieved 两个标记）
   ├ QuestObjInfoBase target  主目标的达成判定
   └ QuestObjInfoBase extra   超额条件的达成判定（没配则为 null）
```

`QuestObjInfoBase` 只负责「达成了没有 / 进度文本 / 描述文案」，发奖和定格在 `QuestObjStateInfo` 里。
类别没有运行时实例，只在存档里记一个 `RewardedCategories` 列表防止重复发奖。

**`QuestManager` 的查询约定**：`GetQuestData` / `GetQuestObjConfigData` / `GetCategory` / `GetQuest`
**取不到就抛 `KeyNotFoundException`**，不返回 null —— 这些 ID 都是配表互相引用出来的，取不到就是没配好，
炸在启动阶段远好过悄悄返回 null、拖到后面某处 NullReference。

要先问「在不在」的，用 `ContainQuestData` / `ContainQuestObjConfigData` / `ContainCategory` / `IsQuestAccepted`，
**别拿 Get 的返回值当存在性判断**。真正「可以不存在」的只有两处：还没领取的任务（面板要画灰卡）、
存档里已从配置移除的任务（读档跳过），这两处都是先 Contain 再 Get。

## 2.2 面板

`QuestPanel`（`Assets/AddressableAssets/Remote/Prefabs/UGUI/Quest/QuestPanel.prefab`）：
左侧类别页签 → 右侧类别说明 + 类别奖励 → 下面每个任务一张卡 →
卡里 `ObjRoot`（每条目标一行 + 目标奖励）＋ `ExtraRoot`（配了超额的目标各一行 + 超额奖励）。

子项（页签 / 卡 / 目标行 / 超额行 / 奖励图标）用**预制体内自带的隐藏模板**克隆，走 `QuestUIPool<T>`，
不单独拆成 Addressables 资源 —— 它们只有这个面板用，拆出去只是多几个 key 要维护。

左侧页签**只列已经领到过任务的类别**（已完成的也算），没碰过的类别连页签都不出现，不提前把后面的内容摊开。
一个类别都没开时显示 `NoCategory`。类别打开后，卡片列表仍然会把该类别里未领取的任务画出来（灰着），那是给玩家的线索。

全事件驱动，不轮询：`OnQuestAccepted` / `OnQuestProgress` / `OnQuestCompleted` / `OnCategoryCompleted` 各触发一次重画
（页签列表每次一并重算，因为新领的任务可能让一个类别第一次冒出来）。

## 3. 事件

没有全局事件总线，任务系统自己开了一个 `QuestEventBus`：**每种事件一个带真实签名的委托**，
目标在 `SubsEvents()` 里只订自己那一种，不会收到无关事件。

天数、道具数量、角色好感这些**已经有各自的变化回调**（`GameDataManager` / `InventoryManager` / `CharacterManager`），
目标直接订那边，不在总线里再转一手。总线只放这些系统没有的事件：

```csharp
// 业务系统上报（一行，任务系统不反向侵入其它系统）
QuestEventBus.ReportMiniGameFinished(gameId, result);   // result: 0 不分胜负 / 1 胜 / 2 负
QuestEventBus.ReportGiftGiven(npcId, itemId, count);
QuestEventBus.ReportItemBought(itemId, count);
QuestEventBus.ReportNpcClicked(npcId);
QuestEventBus.ReportNpcTalked(npcId);
QuestEventBus.ReportDialogueFinished(dialogueId);
```

场景进出与停留由 `QuestManager` 监听 `GameSceneManager.RegisterSceneChange` 自行上报，业务层不用管；
停留计时用协程，且只在「当前场景确实有没领的停留任务」时才起，领完自动停。

`QuestEventBus.ReportQuestCompleted` 由 `QuestManager` 自己在交付时上报，业务层不用管。

**目前这些上报点一个都还没接**（改别人的系统不在本次范围内），所以事件累计型目标暂时不会推进；
状态型目标（天数/道具/好感/对话）订的是各系统已有的回调，接不接上报都能正常工作。
接的时候各加一行，建议位置：

| 事件 | 建议调用点 |
| --- | --- |
| `ReportMiniGameFinished` | 各小游戏的结算处 |
| `ReportGiftGiven` | `GiftManager` 送礼成功后 |
| `ReportItemBought` | 各商店购买成功后 |
| `ReportNpcClicked` / `ReportNpcTalked` | NPC 交互入口 |
| `ReportDialogueFinished` | `DramaUI.Close()` 对话结束时 |
