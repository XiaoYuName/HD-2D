# 任务系统规范（程序侧）

策划原文见 `任务系统相关策划内容.txt`。本文是把它翻译成可配置、可实现的规范。

## 0. 三个概念

| 概念 | 说明 | 配在哪 |
| --- | --- | --- |
| **领取触发**（Trigger） | 一个**瞬间事件**，发生时才去检查这个任务能不能领 | `QuestData.AcceptTrigger` |
| **领取条件**（Cond） | 一个**持续状态**，触发发生时用它做门槛判断 | `QuestData.AcceptCond` → `QuestStoryCondData` |
| **任务目标**（Objective） | 领取后要达成的事，可累计进度 | `QuestData.QuestObjData` / `ExtraQuestObjData` |

策划原文的「领取方式」混了这三类。拆开的理由：

- 「进入区域触发」是事件，只能靠事件驱动；「NPC 数值达标」是状态，事件驱动会漏（数值可能在任何时刻变）。
- 状态判断（道具、好感、天数、前置任务）在剧情系统里也要用，所以独立成 `QuestStoryCondData`，两边共用。

一个任务可以只配触发（不配 `AcceptCond` = 无门槛）、只配条件（不配 `AcceptTrigger` = 等同 `Auto`）、或两者都配。

## 1. 配置写法：位置参数

`AcceptTrigger` / `QuestObjData` / `ExtraQuestObjData` 三列用同一套写法：

```
一条 = 类型:参数1:参数2，多条用 / 分隔
例：DayPassed:2/CompleteGame:1001:2:1
```

- 类型名不区分大小写，各段两边的空白会被裁掉。
- **可选参数一律排在末尾**，不需要就整段省略；要跳过中间的可选参数就填 `0`（表示「不限」）。
- 加新目标类型不用改表结构，只加枚举 + 一个子类。

位置参数没有 key 可对照，所以每种类型在 `QuestManager.BuildConfigCache()`（游戏启动时）报一次自己的写法，
段数不够或某段不是数字会在 Console 直接打出正确写法：

```
[Quest] 任务 10005 的 "BuyItem" 参数不足（需要 1 个，实际 0 个），正确写法: BuyItem:道具ID[:件数]
[Quest] 任务 10005 的 "CompleteGame:1001:两次" 第 2 个参数 "两次" 不是整数
```

### 1.1 领取触发 `AcceptTrigger`

多条之间是 **OR**：任意一个事件发生就尝试领取。

| 写法 | 状态 |
| --- | --- |
| `Auto` | ✅ 读档/任意事件后重扫（不配 `AcceptTrigger` 等同于此） |
| `EnterZone:场景ID` | ✅ 自动接管 |
| `ExitZone:场景ID` | ✅ 自动接管 |
| `EnterZoneStay:场景ID:停留秒数` | ✅ 自动接管 |
| `ClickNpc:NPC ID` | ✅ 需业务层上报 |
| `DialogNpc:NPC ID` | ✅ 需业务层上报 |
| `MiniGameEnd:小游戏ID` | ✅ 需业务层上报 |
| `MiniGameResult:小游戏ID:结果`（1 胜 / 2 负） | ✅ 需业务层上报 |
| `RandomChance:千分比` | ✅ 重扫时掷点 |
| `PlotEnd:剧情ID` | ⏳ 剧情完成记录未实现，永不触发 |

「NPC 数值达标」「游戏时间达到」「任务完成」不做成触发 —— 它们是状态，写进 `AcceptCond` 的
`NpcProp` / `Day` / `TimeSlot` / `QuestPre`。

### 1.2 任务目标 `QuestObjData` / 超额目标 `ExtraQuestObjData`

多条之间是 **AND**：全部达成才算完成。

| 写法（`[]` 内可省略） | 进度来源 |
| --- | --- |
| `DayPassed:天数` | 状态：`PlayerData.Day` 达到 |
| `Dialog:对话ID` | 状态：`DramaManager.HasDialogue` |
| `CompleteQuest:任务ID` | 状态 |
| `HoldItem:道具ID[:数量]` | 状态：`InventoryManager.GetItemCount` |
| `NpcProp:NPC ID:数值[:属性类型]` | 状态，属性类型默认 Goodwill |
| `CompleteGame:小游戏ID:局数[:结果]` | 事件累计，结果 0 不限 / 1 胜 / 2 负 |
| `DialogNpc:NPC ID[:次数]` | 事件累计 |
| `DialogNpcWithItem:NPC ID:道具ID[:次数]` | 事件累计，每次消耗 1 个道具 |
| `GiveGift:NPC ID:礼物ID[:次数]` | 事件累计，礼物ID 填 0 = 任意礼物 |
| `BuyItem:道具ID[:件数]` | 事件累计，道具ID 填 0 = 任意道具 |

策划原文「与指定 1 个或多个 NPC 对话」——**不做「多个 NPC」的复合目标**，写成多条 `DialogNpc` 即可，
天然就是 AND；要 OR 的场景目前没有，真需要时再加，不提前设计。

同理，「1 条鱼 + 2 颗糖」写成两条 `HoldItem`，UI 一条一行各自一个进度。
真要合并成一条显示，就自己继承 `QuestObjInfoBase` 开两个计数字段、重写 `ProgressText` —— 见 1.3。

### 1.3 目标的进度由子类自己管，全靠事件推

基类 `QuestObjInfoBase` 不持有进度，只规定：`IsComplete` / `ProgressText` / `Init` / `Validate` / `SubsEvents` / `UnsubsEvents`。
**没有 Refresh，也没有任何轮询** —— 每个目标订自己那一种事件，订阅时先按当前状态算一次。

| 基类 | 用途 | 子类要实现 |
| --- | --- | --- |
| `StateQuestObj` | 由世界状态算出（持有道具、好感、天数） | `Subscribe()` 订变化事件 + `Evaluate()` 返回当前量；**不进存档**（订阅时重算） |
| `CountQuestObj` | 靠事件累计（打几局、送几次礼） | 订事件，命中调 `Advance()`；只增不减，次数进存档 |
| `QuestObjInfoBase` | 多计数 / 特殊显示 | 自己开字段（要存的加 `[JsonProperty]`）+ 重写 `IsComplete`、`ProgressText` |

各目标订的事件：

| 目标 | 事件源 |
| --- | --- |
| `DayPassed` | `GameDataManager.RegisterPlayerDataDayChange` |
| `Dialog` | `QuestEventBus.DialogueFinished` |
| `CompleteQuest` | `QuestEventBus.QuestCompleted` |
| `HoldItem` | `InventoryManager.RegisterItemIDChangeCallBack`（按道具ID） |
| `NpcProp` | `CharacterManager.RegisterCharacterBagChange`（按角色ID） |
| 累计型 5 种 | `QuestEventBus` 对应事件 |

**状态型**目标随事件重算，回退（比如道具被卖掉）也会跟着回退；**事件累计型**只增不减。

### 1.3.1 存档：直接存目标对象

存档存的就是 `QuestInfo`（含 `List<QuestObjInfoBase>`），序列化器开了 `TypeNameHandling.Auto`，
子类类型写进 json 的 `$type`，所以**子类想存什么类型的进度就开什么字段**（string/float/bool 都行），
不受基类限制 —— 要存的加 `[JsonProperty]`，公开成员不想存的加 `[JsonIgnore]`。

**由配置决定的字段一律不存**（标 `[JsonIgnore]`）：读档后会按当前配置重新 `Init` 一遍，
策划改了数量/条数立刻生效，老存档不会把旧数值冻住。存档实例与配置类型对不上时按配置新建，不炸档。

### 1.4 奖励 `Reward` / 超额奖励 `ExtraReward`

和目标同一套写法，两列搞定。**一种 `QuestRewardType` 一个实现类**，类型名直接就是奖励的东西：

| 写法（`[]` 内可省略） | 实现类 |
| --- | --- |
| `Item:道具ID[:数量]` | `ItemQuestReward`，数量默认 1 |
| `Coin:数值` | `CoinQuestReward` |
| `GameCoin:数值` | `GameCoinQuestReward` |
| `Goodwill:NPC ID:数值` | `GoodwillQuestReward` |

例：`Coin:100/Goodwill:10001:10`。

加一种奖励 = `__enums__.xlsx` 的 `QuestRewardType` 加一项 + 写个 `IQuestReward` 实现 + `QuestRewardFactory` 注册，
和加任务目标完全一样。玩家属性类的直接继承 `PlayerPropQuestReward`，只需给 `PropType` / `DescKey` / `Usage` 三行。

### 1.5 两层校验（触发 / 目标 / 奖励通用）

都在 `QuestManager.BuildConfigCache()`（游戏启动时）跑完：

| 层 | 查什么 | 在哪 |
| --- | --- | --- |
| `Init` 里的 `Require` | 段数够不够、参数是不是数字 | 各实现，正确写法常量在 `QuestTriggerUsage` / `QuestObjUsage` / `QuestRewardUsage` |
| `Validate()` | 道具/角色/任务 ID 在表里存不存在、数值是不是正数 | `QuestConfigValidator` |

因为启动就查过了，运行时**不做空判兜底** —— 查不到就是配置错了，该在 Console 里被看见。

`GetDesc()` 走多语言，Key 常量在 `QuestLocKey.Reward`（`QuestReward/Item` 这种斜杠分段，别写魔法字符串），
文案在 `Assets/0 Core/1 Script/Data/QuestSystem/QuestRewardDataLoc.csv`（表 `LocTableSet.QuestSystem`），
占位符 `{Value}` / `{ItemName}` / `{CharacterName}` 见 `QuestLocVar.Reward`。

任务奖励一般一次性、不复用，所以直接写在任务行里，不走 `RewardData` 索引表。
奖励在 `BuildConfigCache()` 里就解析成对象并校验写法，交付时不再碰字符串。

## 2. 任务状态机

```
None ──触发+条件满足──> Available ──接受──> InProgress ──目标全达成──> ReadyToComplete ──领奖──> Completed
```

- `ReadyToComplete` 与 `Completed` 分开，是为了让「交付」这一步能放到 UI 上（点一下才发奖）。
- 超额目标在进入 `ReadyToComplete` 那一刻定格，达成则交付时额外发一份 `ExtraReward*`。
- 离开 `InProgress` 时目标自动退订事件（`QuestInfo.Deactivate`），已完成的任务不会再吃事件。

## 3. 事件

没有全局事件总线，任务系统自己开了一个 `QuestEventBus`：**每种事件一个带真实签名的委托**，
目标在 `SubsEvents()` 里只订自己那一种，不会收到无关事件。

天数、道具数量、角色好感这些**已经有各自的变化回调**（`GameDataManager` / `InventoryManager` / `CharacterManager`），
目标直接订那边，不在总线里再转一手。总线只放这些系统没有的事件：

```csharp
// 业务系统上报（一行，任务系统不反向侵入其它系统）
QuestEventBus.ReportMiniGameFinished(gameId, result);   // result: 0 不分胜负 / 1 胜 / 2 负
QuestEventBus.ReportGiftGiven(npcId, itemId, count);
QuestEventBus.ReportItemBought(itemId, count);
QuestEventBus.ReportNpcClicked(npcId);
QuestEventBus.ReportNpcTalked(npcId);
QuestEventBus.ReportDialogueFinished(dialogueId);
```

场景进出与停留由 `QuestManager` 监听 `GameSceneManager.RegisterSceneChange` 自行上报，业务层不用管；
停留计时用协程，且只在「当前场景确实有没领的停留任务」时才起，领完自动停。

`QuestEventBus.ReportQuestCompleted` 由 `QuestManager` 自己在交付时上报，业务层不用管。

**目前这些上报点一个都还没接**（改别人的系统不在本次范围内），所以事件累计型目标暂时不会推进；
状态型目标（天数/道具/好感/对话）订的是各系统已有的回调，接不接上报都能正常工作。
接的时候各加一行，建议位置：

| 事件 | 建议调用点 |
| --- | --- |
| `ReportMiniGameFinished` | 各小游戏的结算处 |
| `ReportGiftGiven` | `GiftManager` 送礼成功后 |
| `ReportItemBought` | 各商店购买成功后 |
| `ReportNpcClicked` / `ReportNpcTalked` | NPC 交互入口 |
| `ReportDialogueFinished` | `DramaUI.Close()` 对话结束时 |

## 4. 尚未接通（配置可以先写，运行时会被判为不满足）

- **剧情模块完成记录**：`DramaManager` 只记录到对话粒度（`HasDialogue`），没有「剧情 ID 已完成」的概念。
  `PlotPre` / `PlotEnd` 已留好判定入口 `CondManager.IsPlotFinished`，剧情系统补上记录后改一行即可。
- **游戏评分**：没有任何按游戏 ID 持久化的评分数据，`QuestStoryCondData.GameScore` 列保留但不解析。
- **剧情分支 `Satisfy` / `NotSatisfy`**：列保留，任务系统不使用。
